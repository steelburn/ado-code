# 07 — Tool-Use & Model Routing

**Grades: tool-use A− / routing C+**

Two things that are usually conflated under "function calling". ADO Code's tool
surface is product-grade; its provider layer is broad but is not *routing* in any
decision-making sense.

## Tool-use engineering — A−

### Surface

Around 30 tool definitions in `src/llm/tools.ts` with declared parameter types
(`src/llm/tools/types.ts`), grouped so modes can gate them
([02](02-agentic-engineering.md)). The surface covers file read/write/edit,
search, terminal, git/PR lifecycle, ADO work items, memory, skills, docs
templates, delegation and MCP.

### Batched shapes

Almost every tool that can be called repeatedly accepts an array instead of
forcing repeated round-trips:

| Tool | Batch parameter |
| --- | --- |
| `read_file` | `paths` (up to 10) |
| `get_work_item` | `ids` (up to 20) |
| `edit_file` | `edits` (several disjoint edits, applied in order) |
| `run_terminal_command` | `commands` (each still checked for shell operators) |
| `search_files` | `file_pattern` / `path` / `limit` |

This is the highest-value tool-design decision in the project: **the shape of the
tool API determines how many round-trips a task costs**, and round-trips are the
budget ([04](04-loop-engineering.md)). A tool that only accepts one file per call
forces N iterations for one logical step; the array form makes the batch the
model's natural unit. Per-tool limits (10 files, 20 ids) stop one call from
becoming an unbounded fan-out.

`edit_file`'s `edits` array deserves separate credit: it removes a whole class of
model error, because related edits applied in one call cannot interleave with
their own intermediate state. It also removes the most common cause of double
round-trips ("oops, wrong anchor" then "now the other spot").

### Error contract

Tool errors return JSON `{ error: string }` and never throw (`AGENTS.md`). The
model receives a structured, quotable failure it can act on, rather than an
exception that ends the turn. Every tool is therefore *recoverable by
construction* — the loop stays in control rather than unwinding.

### Consent classes, and tool visibility as a user setting

Consent is per tool class ([03](03-harness-engineering.md)), and whether tool
calls are *rendered* in chat is a single persisted setting
(`adoCode.chat.showToolCalls`) with the host echoing state and the webview gating
every tool-card path on one derived prop. That is a small thing done right: the
toggle has one source of truth, so the transcript cannot disagree with itself
half-way down a run.

### Gaps

- **No bounded retry-with-feedback.** A malformed `apply_diff` returns the error
  to the model, which may or may not adapt; there is no harness-level "retry this
  exact call once with the error attached, then give up" policy.
- **No per-tool success metrics.** Which tools fail most often is currently
  unknown — and unmeasurable without the eval harness in
  [08](08-eval-and-observability.md).
- **No dynamic tool loading.** All in-mode tools are described in every turn.
  With 30 tools that is real prompt cost; a retrieval step ("load file tools
  only") would be cheaper for narrow tasks but is not done.

## Model routing — C+

### What exists

Multiple providers behind one client (`src/llm/providers/openai.ts`,
`anthropic.ts`), base-URL normalisation (`baseUrl.ts`) so OpenAI-compatible
gateways and Anthropic-compatible endpoints both work, shared HTTP handling
(`net.ts`), and `modelCapabilities.ts` for per-model facts — including live
context-window discovery.

That is **provider support**: many endpoints, one interface, correct
normalisation. It is genuinely harder than it looks, and the base-URL work is
what lets users point at any gateway.

### What routing means, and what is missing

| Routing capability | Status |
| --- | --- |
| Choose provider per conversation | yes (user setting) |
| Choose model per *step* by task type | no — condensation, summarisation and tool-arg repair all use the main model |
| Cost- or latency-aware selection | no |
| Mid-run failover on provider error | no — a dead provider fails the turn |
| Automatic downgrade near context limits | no |
| Per-model prompt adaptation | no ([01](01-prompt-engineering.md)) |

The most concrete miss is **cheap-model offloading**: `condenser.ts` rewrites
conversation history and the understanding digest is generated by an LLM. Both
are summarisation tasks where a small, fast model is usually indistinguishable
and an order of magnitude cheaper. Every long run currently pays flagship prices
to compress its own transcript.

## Why these two grades

Tool-use is A− because the *interface design* is better than the tooling most
agents ship: batched shapes aligned to the iteration budget, structured errors,
consent classes, MCP bridging, and a single-source-of-truth visibility toggle. It
stops short of A on the absence of feedback loops around failure.

Routing is C+ because breadth is not routing. Multi-provider plumbing is solid
and makes the product portable across gateways — but nothing in the runtime
*decides* anything, and the one obvious cost win (offload compaction to a cheap
model) is unclaimed.
