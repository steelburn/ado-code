# Codebase Structure Analysis & Agent Reference Files

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Create universal reference files that coding agents (Claude Code, Codex, Cursor, Hermes, etc.) read automatically to understand the project without exploring from scratch. Includes a regeneration script for when the structure changes.

**Architecture:** Three deliverables: (1) `AGENTS.md` — the primary agent-facing codebase reference (standard file all major coding agents auto-read), (2) `.hermes/STRUCTURE.md` — detailed directory/module map with line counts and responsibilities, (3) `scripts/update-structure.sh` — regenerates STRUCTURE.md from the live source tree.

**Tech Stack:** Markdown, bash, wc/find/grep (no new dependencies).

---

- ~258K lines across ~80 TypeScript/TSX source files (excluding node_modules)
- Two-layer architecture: Extension Host (Node.js) + Webview Panel (React)
- Zero runtime dependencies — uses only VS Code APIs and Node.js built-ins
- 83 tests passing, tsc clean
- No AGENTS.md or CLAUDE.md exists yet

```markdown
## Key Patterns

### Tool System
Tools are defined as OpenAI-compatible JSON Schema in src/llm/tools/definitions/.
BaseTool abstract class provides lifecycle (handle → params → execute).
ToolRegistry manages instances and dispatches by name.
ToolExecutor (src/llm/tools.ts) gates tools by mode:
- plan: read-only tools only
- inline: mutating tools require approval hook
- act: auto-approve (with terminal allowlist)

Tool names: get_work_items, get_work_item, read_file, edit_file,
write_to_file, search_files, list_files, apply_diff, run_terminal_command,
delegate_to_agent, restore_checkpoint, call_mcp_tool (mcp__ prefix).

### Message Protocol
src/shared/messages.ts defines the typed contract.
WebviewToExtensionMessage: ~25 message types (userMessage, fetchWorkItems, etc.)
ExtensionToWebviewMessage: ~20 message types (assistantMessage, workItems, etc.)
ChatViewProvider handles all incoming messages in a switch statement.

### Service Composition
createServices() in src/services.ts is the composition root.
AdoClient uses a lazy Proxy so it's not constructed until first use.
Services are rebuilt on org switch or config change.
AgentRunner is constructed separately in activate() and handed to ChatViewProvider.

### Testing
Tests use mocha with suite()/test() (TDD UI), NOT describe/it.
Test files: src/test/suite/<category>/<name>.test.ts
Test runner: @vscode/test-electron (runs in VS Code extension host)
No external test dependencies — uses Node.js assert module.

## Conventions
- TypeScript strict mode, ES modules compiled to CommonJS
- Zero runtime dependencies (only devDependencies)
- No external UI libraries (VS Code CSS variables for theming)
- Workspace-relative paths for file operations (path confinement enforced)
- All ADO API calls use api-version=7.1 (GA) or 7.1-preview.4 (comments)
- Error handling: tool errors return JSON { error: string }, never throw
- Comments use LIVE-TEST FIX / C1-C5 fix annotations for verified behaviors

## What NOT to Do
- Do not add runtime dependencies without explicit approval
- Do not use `any` types where avoidable
- Do not skip the approval hook for mutating tools in inline mode
- Do not use preview API versions where GA exists
- Do not read .env or credential files
- Do not commit without `npm run compile && npm test` passing
```

## Task 3: Create scripts/update-structure.sh

**Objective:** Regeneratable structure analysis script.

**Files:**
- Create: `scripts/update-structure.sh`

**What:** Bash script that walks src/ and generates .hermes/STRUCTURE.md. Run manually or in CI when structure changes.

**Implementation:**

```bash
#!/usr/bin/env bash
# Regenerate .hermes/STRUCTURE.md from the live source tree.
# Usage: bash scripts/update-structure.sh
set -euo pipefail

OUT=".hermes/STRUCTURE.md"
SRC="src"

cat > "$OUT" << 'HEADER'
# Codebase Structure (auto-generated)

> Regenerated by `scripts/update-structure.sh`. Do not edit manually.

## Summary
HEADER

# File counts by directory
echo "" >> "$OUT"
echo "| Directory | Files | Lines |" >> "$OUT"
echo "|-----------|-------|-------|" >> "$OUT"
for dir in $(find "$SRC" -type d -not -path "*/node_modules/*" -not -path "*/.git/*" | sort); do
  count=$(find "$dir" -maxdepth 1 -type f \( -name "*.ts" -o -name "*.tsx" \) | wc -l)
  if [ "$count" -gt 0 ]; then
    lines=$(find "$dir" -maxdepth 1 -type f \( -name "*.ts" -o -name "*.tsx" \) -exec cat {} + 2>/dev/null | wc -l)
    rel="${dir#$SRC/}"
    [ "$rel" = "$dir" ] && rel="."
    echo "| \`$rel\` | $count | $lines |" >> "$OUT"
  fi
done

# Total
total_files=$(find "$SRC" -type f \( -name "*.ts" -o -name "*.tsx" \) -not -path "*/node_modules/*" | wc -l)
total_lines=$(find "$SRC" -type f \( -name "*.ts" -o -name "*.tsx" \) -not -path "*/node_modules/*" -exec cat {} + 2>/dev/null | wc -l)
echo "| **Total** | **$total_files** | **$total_lines** |" >> "$OUT"

# File listing with line counts
echo "" >> "$OUT"
echo "## Files" >> "$OUT"
echo "" >> "$OUT"
echo "| File | Lines | Purpose |" >> "$OUT"
echo "|------|-------|---------|" >> "$OUT"

# Map of file paths to one-line purposes (extend as needed)
declare -A PURPOSES=(
  ["src/extension.ts"]="Entry point: activate() registers providers and commands"
  ["src/services.ts"]="Composition root: createServices() builds all service instances"

  ["src/agents/adapters/GeminiAdapter.ts"]="Google Gemini CLI adapter"
  ["src/changelog/ChangelogService.ts"]="CHANGELOG.md auto-update on task completion"
  ["src/config/settings.ts"]="VS Code settings reader and org selector"
  ["src/config/ContextProxy.ts"]="Cached VS Code globalState/secrets access"
  ["src/git/GitService.ts"]="Git operations: branch, diff, commit"
  ["src/llm/client.ts"]="LlmClient: streaming chat and tool calling"
```

## Additional Recommendations (not in this plan — future work)

These are other things that would assist coding agents:

1. **Dependency graph** — A doc showing which modules import from which (helps agents understand blast radius of changes). Could be generated by `madge` or a simple grep-based script.

2. **API surface index** — List of all exported functions/classes/types per module. Agents often need "what can I call from X?" answers. Could be generated by `tsc --declaration --emitDeclarationOnly` + a script.

3. **Test coverage map** — Which modules have tests, which don't. Helps agents know where to add tests. Could be generated by `c8` or `nyc`.

4. **Common tasks playbook** — Step-by-step recipes for frequent changes: "How to add a new tool", "How to add a new agent adapter", "How to add a new message type". Agents follow these better than general architecture docs.

5. **.cursorrules / .clinerules** — Platform-specific agent config files that point to AGENTS.md. Ensures all agents find the reference.

6. **Lint-staged + pre-commit hook** — Auto-run `npm run compile && npm test` before commits. Prevents agents from pushing broken code.
